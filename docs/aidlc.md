# AI-DLC で回す（ドラマ倶楽部版）

AWS の AI-DLC（AI-Driven Development Life Cycle）の進め方を、noteとXの運用に合わせて置き換えたもの。
決まりは3つ。

1. **フェーズに分けて、フェーズの終わりでオーナーの承認（ゲート）をもらう**
2. **やり取りと決定は全部ファイルに残す**（状態ファイルと監査記録）
3. **AIが自分で見直して、指摘を表にしてから出す**

参考：https://awslabs.github.io/aidlc-workflows/guide/02-your-first-workflow/

## 単位

| AI-DLC | ドラマ倶楽部 |
|---|---|
| Intent（やりたいこと） | オーナーの1回の依頼。例：「今日はLOST10とVIVANTの感想2本」 |
| Unit（作業の単位） | 記事1本 ＝ 1 Unit。Xの投稿一覧・振り返りなども、それぞれ1 Unit |
| Bolt（短い反復） | 1日。その日に公開する分を1回で回しきる |
| Knowledge（共有の知識） | `docs/`（方針・ルール）、`research/`（作品ごとの事実と出典）、`records/`（数字・赤ペン・決定） |

## フェーズ

### 0. Initialization（自動・オーナーの操作なし）

- `CLAUDE.md`・`docs/handover-2026-10-19.md`・この文書を読む
- noteの公開状況をAPIで確かめて、`records/published.md` を最新にする
- Intent のフォルダ `aidlc/intents/<YYMMDD>-<ラベル>/` を作り、`aidlc-state.md` を置く

### 1. Inception（何を作るか決める）→ ゲート1

- オーナーの依頼を、そのまま `audit/audit.md` に書き写す
- Unit に分けて、Unit ごとの要件を `inception/units.md` に書く：作品・話数・記事の種類・切り口（作り手／俳優／主題歌のどれを使うか）・公開日時・タグ（`#作品名第N話` を含む）・マガジン
- 決められないこと（例：オーナーがその回を見たか）は質問にする。質問は `inception/questions.md` に、選択肢つきで書く
- **ゲート1**：オーナーが「Approve」か「直して」と返す。オーナーの依頼の中で作品・本数がはっきりしていれば、そのまま承認とみなして進めてよい（このとき audit にそう書く）

### 2. Construction（作る）→ ゲート2

Unit ごとに、次の順で進める。リサーチは Unit をまたいで並列に走らせる。

| ステップ | やること | 出力 |
|---|---|---|
| 2.1 リサーチ | 事実・反応・作り手と俳優と主題歌の背景を集める | `research/<作品>.md` |
| 2.2 事実確認 | 本文で使う事実を、公式かニュースで確かめる。Wikipediaやブログだけのものは使わない | `research/<作品>.md` に出典URL |
| 2.3 執筆 | 本文・タイトル・タグ・マガジン | `articles/<日付>/<作品>-<話数>.md` |
| 2.4 見出し画像 | `design/make_header.py` で作り、96px・211px で読めるか見る | `articles/<日付>/<作品>-<話数>_header.png` |
| 2.5 X告知 | 告知文 | `x/<日付>.md` |
| 2.6 セルフレビュー | 下のチェック項目で見直し、指摘を表にする | `construction/review.md` |
| 2.7 入稿キット | `tools/build_kit.py` で作り、Artifact を更新 | `articles/<日付>/kit.html` |

**セルフレビューのチェック項目**（`CLAUDE.md` と引き継ぎ資料のルールから）

- 事実：全部に出典があるか。放送前の作品で公式外の情報を書いていないか
- 著作権：公式画像・歌詞・他人の文面を使っていないか。台詞は短く、第何話かを書いたか
- 人物：NGの噂に触れていないか。見た目をけなしていないか
- 口調：口語調か。人名は呼び捨てか。断定・煽り・他作品を下げる比較がないか
- 型：タイトルは作品名から30字前後か。【ネタバレ】の表記。2,400〜4,500字・見出し7〜11。タグ5〜8（作品名タグ・`#作品名第N話` を含む）。`#ドラマ感想文` はその日1本だけ
- 切り口：作り手・俳優・主題歌のうち2つ以上あるか
- 体験：オーナーが見ていない回で、見た感想のふりをしていないか

**レビュー表の書き方**

| ID | 重さ | 場所 | 指摘 | 状態 |
|---|---|---|---|---|
| R1 | 高／中／低 | 記事・見出し | 何がどうまずいか | 直した／残す（理由）／オーナー判断 |

「高」が残っている間は、ゲート2に出さない。

**ゲート2**：入稿キットとレビュー表をオーナーに渡す。オーナーの返事は3通り。

- **Approve**：残っている指摘を受け入れて、公開へ
- **直して**：赤ペンを `records/redpen.md` に書いてから直し、もう一度ゲート2
- **この指摘は不要**：IDと理由をもらい、レビュー表に書く

### 3. Operation（出す・測る・学ぶ）

- 3.1 公開：オーナーが note で公開、X で告知（Claudeはしない）
- 3.2 記録：オーナーからもらったURLと時刻を `records/published.md` に。告知文のURLを確定
- 3.3 計測：日曜にオーナーから数字をもらい、`records/` に記録
- 3.4 振り返り：週の振り返り。赤ペンが同じ内容で3回出たら `CLAUDE.md` のルールに格上げ。型を変えたら `records/decisions.md` に根拠と結果

## ファイル

```
aidlc/intents/<YYMMDD>-<ラベル>/
  aidlc-state.md        どのフェーズ・ステップまで進んだか（Unitごとのチェック）
  audit/audit.md        オーナーの依頼・承認・赤ペンを原文のまま、時刻つきで
  inception/units.md    Unitごとの要件と計画
  inception/questions.md オーナーへの質問（あれば）
  construction/review.md セルフレビューの表
```

成果物そのもの（記事・画像・X投稿・リサーチ）は、これまでどおり `articles/`・`x/`・`research/` に置く。intent のフォルダには「何を決めて、どこまで進んだか」だけを置く。

## 進め方の選択

ゲートの細かさはオーナーが選べる。決めていなければ「まとめて確認」で進める。

- **まとめて確認**（標準）：ゲート1は依頼がはっきりしていれば省略、ゲート2で全 Unit をまとめて見てもらう。1日30分に収まる
- **1本ずつ確認**：Unit ごとにゲート2を出す
